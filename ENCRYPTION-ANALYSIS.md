# GameMaker GMD Recovery — encryption analysis

Investigation into whether the encryption key can be recovered from the `.exe`
on disk instead of by launching the game and scanning its memory.

**Bottom line: memory extraction stays the practical method.** File-only
recovery is proven for GameMaker 5.0 and nearly complete for 5.1, but the
5.3/5.3a family — which is the majority of the sample set — uses an
unstructured permutation that resisted every attack tried here. GM 6.x uses a
container that has not been identified.

One part of the work is worth adopting regardless of which route is used: the
data header can be located in the file with no knowledge of the key, which
gives the GameMaker version and the exact data offset far more reliably than
the current hardcoded offsets.

---

## 1. How the protection works

It is a monoalphabetic byte substitution — a single fixed 256-byte permutation
applied to every byte of the appended game data. `DecompileExe` in
`frmMain.frm:1127` builds the inverse and applies it:

```vb
NewArray(Asc(Mid$(key, i + 1, 1))) = Asc(Mid$(Unencrypted, i + 1, 1))
...
Temp2 = NewArray(Temp)
```

So `key[plaintext] = ciphertext`, and the app derives the decrypt table itself.
Any 256-byte file loaded through **Options → Override encryption key → Browse**
(`frmOptions.frm:160`, `frmMain.LoadKeyByFilename`) must be in that layout.

### Known plaintext

The game data always begins with the dword `1234321` (`91 D5 12 00`) followed
by a version dword. `FindGMDStartOffset` already relies on this — it searches
the decrypted stream for `Chr(145) & Chr(213) & Chr(18)`.

Version dword values seen: 430=`0x1AE`, 500=`0x1F4`, 510=`0x1FE`, 520=`0x208`,
530=`0x212`, 540=`0x21C`, 600=`0x258`, 610=`0x262`, 700=`0x2BC`, 800=`0x320`.

`E(0) = 0` held in every sample examined, so plaintext zero bytes survive
encryption unchanged. That is what makes the header findable.

### Locating the header without the key

A substitution is injective, so the **equality pattern** of the eight header
bytes alone identifies the version — no assumption about the key is needed.
Search for a position where bytes 3, 6, 7, 8, 9, 10, 11 are zero and bytes
0, 1, 2, 4, 5 are non-zero, then test which version makes the equality pattern
consistent. This found the header in **10 of 10** sample executables.

## 2. Key families

Classify by the per-byte deltas `ciphertext - plaintext` across the five
non-zero header bytes:

| Family | Deltas | Meaning |
|---|---|---|
| `identity` | `[0]` | data not encrypted |
| `adjacent` | subset of `{-1, 0, +1}` | every byte maps to itself ±1 |
| `near-shift` | span ≤ 1, e.g. `[39, 40]` | constant rotation plus jitter |
| `full` | unstructured | arbitrary permutation |

### The `adjacent` family is fully enumerable

Every key in this family is an involution built from **exactly 94 swaps of
adjacent pairs at odd indices**, leaving 68 fixed points. That reduces the key
to 127 yes/no bits, and every observed bit pattern is generated by

```
pair i (i = 0..126) is swapped  iff  ((i * a + c) mod 127) < 94
    swapping byte values (2i+1, 2i+2),  a = 1..126,  c = 0..126
```

16002 `(a, c)` pairs collapse to **8001 distinct tables** — a complete keyspace
small enough to search exhaustively.

### The key files already in this repo

| File | Structure | In the 8001 set |
|---|---|---|
| `final50.txt` | involution, 94 swaps, 68 fixed | yes — `(a=19, c=94)` |
| `final60.txt` | involution, 94 swaps, 68 fixed | yes — `(a=12, c=19)` |
| `key6.1.txt` | involution, 94 swaps, 68 fixed | yes — `(a=41, c=27)` |
| `bothkey.txt` | byte-identical to `key6.1.txt` | yes — `(a=41, c=27)` |
| `final51.txt` | not an involution; 179 entries at delta `0xD5` | no — near-shift family |
| `bruteforcekey.txt` | **not a permutation at all** | no — almost certainly a false positive from `frmBruteForce` |

`bothkey.txt` is a derived artefact: `DecompileExe` writes it in the 5.3a/5.4
branch after its `BeginKey`/`EndKey` rearrangement. It being an exact duplicate
of `key6.1.txt` means it is stale, not a genuine 5.3a key.

`frmBruteForce.vaildKey` already tests permutation validity, and the
`Num = 32640` check is the sum of 0..255 — both correct tests, just applied to
a memory dump rather than to the file.

### GM 5.0 — solved

The 8001-key search on `CosgroveUmbrella.exe` returned 85 tables matching the
8-byte header. Ranking them by GameMaker's own string-length consistency (count
of `L 00 00 00` dwords followed by exactly `L` printable bytes) plus a byte
bigram score selected the correct key. Output is exact:

> "10 levels of action-packed arcade fun are maxed out in this platform-style
> game. Guide Cosgrove the blob through three worlds to help him find his way
> home and defeat the weather demon, Meese." — by "Ben Roth"

with resource names `enemy1_right`, `blob_climbing`, `switch_activated`,
`life_display`.

### GM 5.1 — 254 of 256 bytes

`5.1.exe` decrypts to readable content — *"This is a Link to the Past style, 3D
remake of Ocarina of Time"* by "Daniel Carras", plus `sndstartup`,
`sndbeginning`, `sndbombexplode`, `sndlinkhurt`. Two table entries stay wrong
(rendering "Carras" as "Barras" and "3D" as "2D"); the true table has an
irregular entry beside each, which a statistical model cannot see. Fixing those
requires a GameMaker format walker that validates string-length prefixes.

### GM 5.3 / 5.3a — not solved

Three samples, all with the header at file offset **1500037**. Note
`eOffset53a = 1500000` in `modGlobals.bas` was only 37 bytes away.

Their keys are unstructured permutations, so neither the 8001-key search nor
the shift trick applies. Two attacks were tried and both failed:

1. Iterated Hungarian assignment with a byte bigram model.
2. Simulated annealing, 4 restarts × 60000 iterations, scored against a 3.3 MB
   domain model built from `breakout.gm6`, `effect_demo.gm6`, `regdemo61.gm6`
   and `sweetdreamsSOURCE.gmd`.

Validation used strings that genuinely exist in `Lagrange.gmd`: **0 of 200**
were recovered. The plaintext structure is clearly intact — resource names
repeat at the right offsets — but most of the stream is image and sound data,
which swamps the text signal a bigram model depends on.

The matched `.gmd` files could not supply exact ground truth: `Lagrange.gmd` is
version 500 and `sweetdreamsSOURCE.gmd` is version 510, while both executables
embed version 530, so the layouts differ and byte alignment breaks after ~44
bytes.

### GM 6.x — container not identified

For `breakout.exe` and `regdemo61.exe` the only header found is the
included-files block (`D3DX8.dll` plus a zlib stream) at exactly 1600000. The
real game data sits in the ~27 KB before it, is not plain zlib, and none of
`breakout.gm6`, `regdemo61.gm6` or `effect_demo.gm6` appears verbatim anywhere
in its own executable. So GM 6.x data is neither stored in the clear nor in a
format recognised here.

### `3d-test.exe` is not a game

It is a self-extracting wrapper. The zlib stream at offset 430064 decompresses
to 1491456 bytes that are **byte-identical to `3d-test1.exe`**.

## 4. Current version detection is unreliable

`VersionCheck` (`frmMain.frm:836`) reads version strings at hardcoded absolute
offsets. Against these samples it identifies **5 of 10**:

| Result | Samples |
|---|---|
| detected | `5.1.exe`, `CosgroveUmbrella.exe`, `Lagrange.exe`, `Restaurant.exe`, `sweetdreamsSOURCE.exe` |
| missed | `3d-test.exe`, `3d-test1.exe`, `breakout.exe`, `effect_demo.exe`, `regdemo61.exe` |

The misses are not subtle. `3d-test1.exe` carries `Game_Maker 5.4` at 637293
while the code reads 631505. Every GM 6.x file has `TRunnerForm` at 1011057 or
1327961 while the code reads 557270.

Replacing those seeks with a search for the marker string — or better, with the
header detection in §1, which worked on all ten files — fixes this. It helps
the memory-dump workflow too, since picking the wrong version selects the wrong
key signature and the wrong data offset.

## 5. Tooling

`tools/filekey.py` implements the above. Requires numpy and scipy.

```
python tools/filekey.py <game.exe> [...] [-o OUTDIR]
```

For each input it reports the appended-data offset, the header offset, the
GameMaker version and the key family. Where it can recover a key it writes:

* `<name>.key.txt` — 256 bytes in the layout `LoadKeyByFilename` expects, so it
  loads directly through **Options → Override encryption key → Browse**
* `<name>.gmd` — the decrypted data stream

The key file was verified by running it through the exact `NewArray`
construction from `DecompileExe`; it reproduces the correct plaintext.

## 6. Recommendations

**Keep memory extraction as the primary path.** It is the only method that
currently works for 5.3/5.3a and 6.x, which is most of the sample set.

**Adopt file-based header detection anyway.** It is roughly 120 lines of VB6,
needs no key, works on every sample, and replaces both the hardcoded
`VersionCheck` offsets and the hardcoded `Seek` values in `DecompileExe`. It
improves the memory workflow rather than competing with it.

**Optional: add the 8001-key search for GM 5.0.** Another ~120 lines, validated
end to end. It removes the memory dump entirely for that version. Because ~85
keys typically match the 8-byte header, it needs the ranking step, which fits
the existing "pick an offset from the list" UX in `frmBruteForce`.

**Unrelated but worth doing:** `DecompileExe` reads the file one byte at a time
(`Get #2, , Temp` across ~1.5 MB), and the search paths go through
`RichTextBox1.LoadFile` + `.Find`, which is unreliable on binary data. Reading
into a `Byte()` array with a single `Get` would speed the tool up dramatically
on its own.

## 7. Open questions

* What generates the 5.3/5.3a permutation? A `.gmd` **saved by GM 5.3a itself**
  (version 530) next to its compiled exe would give byte-exact ground truth for
  the key and settle whether any structure exists.
* Where does GM 6.x put the game data, and how is it encoded?
* Do the `(a, c)` parameters of the 8001-key space correlate with anything
  visible in the file? If so, even the search could be skipped.
